# Example: Rich Context

## Input

**Product:** Developer documentation platform
**Target segment candidates:** (a) individual developers, (b) developer-focused startups (5–50 engineers), (c) mid-market SaaS companies with dedicated developer relations teams
**Product capabilities:** AI-assisted doc writing, auto-sync with codebase, versioning, embeddable API reference, analytics on doc usage
**Business goals:** Move from PLG individual signups to team/company contracts; grow ACV from $800 to $8,000
**PMF signals:** Strong retention among devrel teams; high churn among solo developers (wrong ICP for paid)
**Win/loss context:** Win when there's a devrel or developer-facing product team; lose to Notion/Confluence when IT buying controls the decision

## Output

### Target segment
Developer-facing SaaS companies (20–500 employees) with a dedicated devrel function or developer-facing product — teams that ship APIs, SDKs, or developer tools and need documentation that stays current as the product evolves.

**Explicit exclusions:**
- Solo developers and indie projects (low willingness to pay; high churn)
- Enterprise IT-controlled procurement (lose to Confluence/SharePoint on incumbency)
- Non-technical teams writing general product or help documentation (wrong product for the job)

### Frame of reference
Developer documentation platforms (competing with GitBook, ReadMe, Mintlify, and internal Notion/Confluence setups).

### Point of differentiation
The only documentation platform built around the live codebase — docs stay in sync with the product automatically, so devrel and engineering teams stop maintaining stale documentation.

### Reason to believe
- Auto-sync with GitHub/GitLab repos pulls code changes into docs without manual updates
- API reference is generated directly from OpenAPI specs, always current
- Usage analytics show which docs developers actually read — so teams know what's missing

### Positioning statement
For developer-facing SaaS teams, [Product] is the documentation platform that keeps docs in sync with your codebase — so your developers stop shipping outdated docs and your users stop filing tickets for information that already exists.

### Positioning trade-offs
This positioning sacrifices:
- General-purpose writing teams (they'll use Notion/Confluence)
- Solo developer market (too price-sensitive for the ACV we need)
- Non-code-adjacent documentation (user guides, HR wikis, etc.)

### Confidence level
Context-informed — PMF and win/loss signals support segment choice; positioning should be validated with 5–10 customer interviews before locking in for GTM.
