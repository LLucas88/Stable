## Input
We're a small product team and we don't have any documentation. Onboarding new people is painful. We want to build a product wiki. We use Confluence.

## Expected output
Wiki purpose and primary use cases (provisional):
Primary use case identified: onboarding. This is a good starting point — build only what's needed for onboarding first; don't try to document everything at once.

Top-level structure (provisional):

```
Product Wiki (Confluence)
├── Start Here (onboarding)
├── How We Work (process guides)
├── Templates
└── Reference
```

This is a minimal structure. Expand only as needed — an empty wiki with a clear structure is more useful than a cluttered wiki with no navigation.

Content types (provisional):
- Process guides: where things currently live is unclear — what processes need to be documented first?
- Templates: which templates does the team use repeatedly?

Content ownership map:
Not defined. For a small team, each section needs one named owner — otherwise content goes stale immediately.

Freshness system:
For a small team: put a "Last reviewed" date on each page and review quarterly. Keep it simple.

Tool boundary definition:
Not defined. What tools does the team use for tickets, communication, and documentation? The wiki needs to have a clear boundary with other tools or it becomes a dumping ground.

Maintenance plan:
Not defined. Start with a simple rule: if you have to answer the same question twice in Slack, write it in the wiki.

Missing information:
- Team size and composition
- Which specific onboarding gaps are most painful (what do new people ask most?)
- Repeated Slack questions — these should be the first pages written
- Whether the team has any existing process documentation to migrate

Quick start recommendation:
Don't design the full structure first. Interview one recent new joiner: "What took you the longest to figure out?" Write those three pages. That's the first sprint of wiki work.
