# Stable Agent 综合性能测试：真实模型阶段

报告整理：2026-10-26。实际调用：2026-10-24 北京时间约 00:34–00:44；原始 JSON 使用 UTC 时间。

## 结论

功能链路可用，但存在可复现的冗余：普通知识问答仍执行需求判断、正式回答、消息预测三次模型请求；新会话首轮把当前请求同时写入历史和当前请求区，导致大段数据重复；持久会话续聊每轮重复追加规则与完整技能目录。应先处理这三项，再评估 CLI 进程复用。

本次仅诊断。没有修改产品代码、打包、部署或推送。测试开始时已有的未提交修改全部保留。六个关键执行文件的 SHA-256 与测试开始记录一致。

## 已验证问题及优先级

### P1：普通问答的辅助调用仍然过多

简单知识问答两次都执行：textOnly 需求判断 → 正式回答 → message-prediction。第一轮需求判断 7.358 s、正式 Runner 7.927 s；第二轮需求判断 4.190 s、正式 Runner 7.726 s。需求判断实际占用了主回答关键路径。

预测发生在答案返回之后，额外完整等待 3.551 / 3.636 s，其中预测 Runner 为 2.955 / 3.193 s。不要把预测时间加进上述主回答耗时，也不要忽略其额外费用和进程占用。身份问答没有预测模型请求，说明跳过机制只覆盖部分场景。

建议：对明确、低风险的知识问答跳过独立需求判断，交给执行模型在真正缺信息时提问；短回答按需提供预测。权限审批、有副作用操作及待回答问题必须保留。当前测到的判断耗时是可优化阶段，不等于已经证明修复后必然节省相同秒数。

### P1：首轮当前请求被完整重复一次

SDK 会话日志中，第一批 2,000 条合成数据连续文本长 127,757 字符，在首个 user 消息中精确出现 **2 次**。首个 user 消息总长 279,595 字符。

代码路径对应：`desktop/main.cjs:2399` 先提交当前用户消息；`desktop/main.cjs:1753` 随后读取 recentContext；`desktop/main.cjs:1787` 组装 initialPrompt。`desktop/services/prompts.cjs:106` 写入最近对话，末尾又写当前请求。`desktop/services/claude-harness.cjs:293` 在会话尚未 seeded 时发送 initialPrompt。

建议：按当前消息 ID 排除已单独放入“当前请求”的那一条，保持旧历史不变。不能按内容去重，用户有意重复发送同一句话是合法行为。需要验证新会话、旧会话导入、澄清补充、断点恢复，以及附件只出现一次。

### P1：续聊反复追加静态规则和技能目录

虽然续聊清空了 composeAgentPrompt 的 history 参数，函数仍每次插入全局规则、执行约束及 18 项技能目录。SDK 持久会话本身已保留之前消息，因而这些内容不断累积。

最后两次短请求实际构造成 36,493 / 36,542 字节的新 user 消息，公共前缀长 23,798 字符。模型输入由 224,408 增长到 233,510，再到 242,614 tokens，约每轮增加 9,100 tokens。不能把这些 token 全算作模板：其中还包括前一轮回答等；但模板重复本身已有直接证据。

建议：稳定规则与技能目录在会话初始化时注入，续聊只发送本轮内容与必要变更；用版本或摘要识别规则变化。切换模型、账号、权限、工作目录、技能时必须正确更新，不能以省 token 为由漏掉新权限约束。保持原有稳定前缀有利于缓存，不宜每轮整体重排。

### P2：SDK 进程初始化仍有固定开销

此次已预加载 SDK。GLM 第一次主 Runner 的原生初始化为 2.752 s，后续各阶段约 1.059–1.605 s（processSpawn 到 sdkInitialized）。辅助判断和预测也各自支付这笔开销。

建议先减少多余 Runner，再评估同会话有界进程复用。需要账号/权限隔离、取消、崩溃恢复、空闲回收和内存上限。此前本地模拟对照未证明 textOnly 单独就能显著提速；不能把 JS import 缓存等同于 CLI 已常驻。

### P2：工具校验方式增加了无效修复轮次

创建任务的计算结果正确，但 Agent 用 grep 查找不带千分位的合计，遇到 `MISSING:58300`，随后又调用模型修正为格式化数字检查。测试评分器也独立犯了同类错误。

建议：JSON 数值核验与 HTML 展示核验分开；表格应解析后比较数值，避免用单个文本 grep 判定报告正确性。独立校验可以在同一次脚本执行中完成，但不要把所有互相依赖的动作盲目并行。该任务的 9 次调用并非全属浪费，读取、执行和交付确认仍有必要。

## DeepSeek、网络与机器负载

DeepSeek 第一笔请求返回 HTTP 402，客户端明确提示“模型供应商余额不足或付款受限；不是 Stable 账号额度不足”。仅请求一次，没有持续重试，账单释放且实际费用为零。此次没有获得 DeepSeek 正常回答，因此无法评价它当前的速度和质量；也不能把测试时的余额状态当作报告日仍未充值。

这次失败总耗时 20.162 s：Runner 前约 1.675 s，Runner 到发请求约 6.223 s，HTTP 等待 10.303 s，HTTP 后约 1.961 s。网关同笔请求自身耗时 413 ms，说明延迟还有网关处理之外的部分，但不能跨机器直接相减绝对时间来归因。

当时客户端走系统代理，启动日志出现一次网络服务重启。之后通过同一 Chromium 代理路径请求无推理的 health 接口三次，分别 432.718、58.399、56.342 ms，全部成功。这不足以断言代理持续故障；需要带同一请求 ID 的分段传输计时和可控对照。

主机总内存约 15.73 GiB，测试期间有快照可用内存约 1.13 GiB。未采集分页、磁盘 I/O 与低负载对照，不能认定慢样本由换页造成。没有关闭用户应用来制造理想环境。

## 后续修复验收建议

1. 优先修正首轮去重、续聊增量上下文；对同一合成数据重放，检查原始文本只出现一次、短续聊不再重复完整目录，同时验证会话恢复与权限更新。
2. 减少简单问答的前置判断和自动预测；验收标准是明确短问答只需一次主模型请求，不误跳过真正的澄清或权限审批。
3. 再测 CLI 复用、工具校验和网络分段；使用相同模型、提示、机器负载分组测试。真实 A/B 需要新的费用授权，不能把剩余额度当作无限期许可。

本次没有并发压力、图像生成、截图审阅、前端渲染、取消竞态或 1M 极限测试；不报告这些能力通过。
