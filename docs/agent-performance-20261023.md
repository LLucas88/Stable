# Agent 性能诊断（2026-10-23）

## 范围与结论

测试对象：`D:\stable` 当前工作区，Stable 1.11.0、Claude Agent SDK 0.3.308、实际 CLI 报告 2.1.308。包含现有未提交修改，不等同于之前生成的安装包。

本轮使用真实 SDK、真实本地桥接、真实 Read/Bash，以及隐藏的 Stable 主进程发送 IPC；模型服务全部替换为内存中的确定性响应。没有调用真实付费模型、没有读取或复制原账号凭据/历史，没有修改产品源码、打包、部署或推送。测试夹具只使用新建数据目录。

最优先的问题是普通问答仍会启动独立的需求判断和消息预测。SDK 每次运行都启动并结束一个 CLI 进程，使这两个辅助步骤也承担初始化开销。当前证据支持先减少辅助调用，不能证明“关闭工具即可显著提速”。

**以下耗时均为免费模拟上游的本地开销，不是 DeepSeek 的真实响应速度。** 本轮尚未取得新的真实模型费用上限确认，未执行付费阶段。

## 完整发送链路

使用全新临时用户目录，启用消息预测，模拟 Cloud 登录和路由，保留真实 `stable:agent:run`、`stable:agent:prediction`、SDK 和本机代理。每次先通过真实选择会话 IPC 切换活动会话。隐藏窗口不加载前端；不测绘制、输入事件或网络服务排队。预加载返回成功。

按“身份问题、知识问答”交替运行三轮，模拟模型立即返回固定短文本；正式回答内容本身不作模型质量评分。耗时从调用发送 IPC 至返回，预测单独计时。

| 场景 | 保存回答（3 次） | 回答耗时中位数 | 回答后预测 | SDK / 请求数 |
|---|---|---:|---:|---:|
| 你是什么模型 | 2.027 / 2.310 / 2.071 s | 2.071 s | 约 0.001 s，无模型请求 | 每轮 1 / 1 |
| 用一句话解释什么是缓存 | 3.899 / 3.724 / 3.852 s | 3.852 s | 1.817 / 1.841 / 1.684 s | 每轮 3 / 3 |

知识问答的三个阶段为：

1. `textOnly` 需求判断：1.763–1.863 s，本轮 mock 返回 ready。
2. 实际回答：1.790–2.009 s。
3. `message-prediction`：1.666–1.822 s，mock 返回无建议仍已发生一次请求。

包括预测的整条后端链路为 5.536–5.716 s。**预测不在发送 IPC 的回答等待时间内**；前端还有 300 ms 防抖，本测试主动调用预测 IPC，没有把这 300 ms 算入。

正式回答请求约 76,136–76,166 字节，包含 8 个工具；需求判断约 24,134 字节；预测约 2,719 字节。字节数不能当作 token 数，mock usage 是测试常量，不能用它估算费用或实际上下文占比。

证据：`../.local/agent-performance-20261023/ipc-EA30xZ/result.json`。

## SDK 与工具分阶段测试

以下为直接调用 Harness 的独立夹具，不加载主进程的完整技能/设置，不能直接与上一表作 A/B 比较。

| 场景 | 样本 | 本地总耗时 | 说明 |
|---|---:|---:|---|
| 测试进程的第一次运行 | 1 | 5.966 s | spawn 到 SDK 初始化 4.638 s；未清空系统缓存，不称为严格冷启动 |
| 后续新会话 | 3 | 1.787–2.514 s，中位数 1.846 s | 每次仍启动独立 CLI |
| textOnly | 3 | 1.848–2.164 s，中位数 1.879 s | 与完整工具路径区间重叠，无显著加速证据 |
| 同会话续聊 | 3 | 2.029–2.378 s，中位数 2.369 s | 继承历史，但仍启动进程 |
| 长历史续聊 | 1 | 2.336 s | 请求约 656,587 字节；只验证序列化/续接，不代表真实模型长上下文性能 |
| Read → Bash → 回答 | 2 | 5.996 / 4.072 s | 真实读取测试文件和执行 printf，共 3 次模拟推理请求 |
| 供应商 HTTP 402 | 2 | 2.717 / 2.754 s | 都仅请求 1 次，明确失败，无持续重试 |

后续普通运行的 SDK 模块导入约 0.02 ms；完整主进程里约 0.3–5 ms。相比之下，主进程验收的每次 CLI 初始化约 1.273–1.589 s，占本地步骤的大头。上下文统计在完整发送验收约 22–42 ms，没有出现代码中允许的 2.5 秒等待上限，不应优先删除这项正确性保障。

工具测试原始两轮失败是夹具未设置 Bash 所需的 `networkAccess`，随后 mock 错误处理反复抛异常引起重试；不是应用在正常授权下的工具故障。保留原始失败记录，修正夹具授权配置后两轮均通过。全流程初次夹具没有切换活动会话，因此预测未触发；补齐真实选择会话操作后，最终六轮均通过。没有为使测试通过而改变产品源码。

## 问题与优化优先级

### P1：普通明确问答的前置判断可以省掉

已验证：`clarification.cjs` 的确定性跳过规则覆盖问候、身份、能力、感谢。`1+1等于几？` 和简短知识问答仍调用 `ask`；完整发送链路也复现了独立需求判断请求。

建议：让明确、低风险问答进入执行模型，由它在真正存在信息缺口时提问；不要为了判断是否需要判断再新增一个模型请求。已有待回答问题、附件引用、权限待决和有副作用的操作必须继续保留相应边界。预计可避免一次 SDK 初始化和一次上游调用；真实节省秒数需付费 A/B 验证，本轮不能承诺。

### P1：消息预测应减少无收益调用

已验证：知识问答完成后，预测会额外启动一个 SDK 并请求模型，即使最终返回 null。300 ms 防抖主要过滤快速切换，不能避免用户停留阅读时发起推理。

建议：对无行动性短回答采用确定性跳过；或者按用户实际需要触发建议，并保留开关。不要把预测追加时长误计入主回答延迟。主任务到来应优先取消预测，之后才评估是否恢复。

### P2：减少 CLI 重复启动，而非只优化 JS import

已验证：`run()` 每次 spawn，在 finally 中关闭并回收；预加载只共享模块和执行一次 `--version`，不会保留可直接接收下一轮输入的 Agent。textOnly 仍支付 CLI 初始化成本。

建议：先消除多余 Runner，再评估同会话有界复用。复用必须在模型、账号、权限、工作目录、技能/插件变化时失效，处理取消、崩溃和资源回收，并限制数量/空闲时间。不能把不同账号或权限上下文的进程混用。

### P2：按需加载上下文，但先测收益

已验证：新建测试数据下，简单身份问题也发送约 76 KB 请求。它包含通用 Agent 指引和工具说明，仍有精简空间。直接 Harness 中 textOnly 的请求从约 44 KB 降到约 20 KB，但本地耗时没有稳定改善。

建议：拆分始终需要的规则和按任务加载的能力说明，保持已有缓存前缀稳定。不要删掉权限规则或用广泛正则裁剪用户历史。新会话、续聊、模型切换、截图、工具发现均需复核。

### P2：内存压力需要独立归因

已验证：主机可见内存约 15.73 GiB；本次两个系统快照的可用内存约 0.84 / 0.75 GiB。没有主动关闭用户应用。

这说明测试处在较紧张的内存环境，但没有分页故障、磁盘 I/O 或低负载对照证据，不能断言某个慢样本由换页造成。后续应在可用内存充足和当前负载两种条件下重复相同用例，记录进程树内存/CPU峰值，再决定并发限额与闲置回收策略。
