## 发布顺序

1. 部署前 SSH 曾拒绝现有密钥。本地私钥存在，历史授权曾绑定来源 IP；不能凭 HTTPS 代理出口推定 SSH 来源。用户恢复公钥后本次已成功连接，并按实际来源重新收紧限制。现有云 API 凭据的精确 IP 查询未找到该实例，未使用其部署。
2. 通过远端管理员控制台恢复现有公钥。恢复脚本先备份授权文件。登录后立即以实际 SSH_CONNECTION 的来源 IP 恢复 /32 限制。
3. 读取线上 current、源文件哈希、数据库位置和健康状态，确认本地补丁基于线上版本。等正在执行的请求结束再切换。
4. 执行既有加密备份及恢复校验，保留旧发布目录；对账号和历史相关数据建立校验基线。
5. 在新发布目录构建；执行 0010、0011 增量迁移，创建三个独立工具服务及新价格版本。先验证服务器官方供应商 Key 可用，只报告配置存在与否，不打印凭据。
6. 切换 current 并健康检查。异常恢复旧发布目录，不用旧数据库覆盖切换后的账务数据。保留新增表、请求、幂等结果和账务记录。

## 真实验收计划（总上限 5 元）

- 使用隔离测试数据、原账号凭据；不修改原账号配置或聊天历史。
- 每次付费请求前核对剩余预算并预留最坏成本；供应商余额失败立即停止该路径，不循环重试。包含搜索、抓取、生图及聊天 token 费用。
- 相同问题、相同聊天模型比较旧搜索和新搜索链路，分别记录总耗时、工具耗时、模型请求次数、输入/输出 token、账单；冷启动与连续调用分别记录，不将单次样本视为普遍提升。
- 验证搜索→抓取→回答引用的完整链路，并验证 GLM-image→图片查看→交付。无结果、失败和幂等重放检查不得重复扣费。
- 先检查旧链路是否可运行；若供应商余额或模型可用性不同，明确标记无法直接 A/B，不用不同条件伪造性能改善。

### 同机搜索对比

三个配对样本均从同一网关服务器调用同一 DeepSeek 账号、相同查询；新接口 `count=3, need_content=false`。旧请求复用原 Stable 的 Messages + web_search 结构，但为控制测试成本将旧 `max_uses=5` 限为 1，保留 `max_tokens=4096`。旧服务内部仍返回 10 项，原客户端最终会裁成 3 项。这是旧 DeepSeek 直连搜索方式对比；旧 Stable Cloud 搜索本来未接通，不能声称与一个此前可用的云搜索作 A/B。

| 样本 | 新独立搜索 ms | 旧 Messages 搜索 ms | 旧 input_tokens | 旧 cache_read_input_tokens | 旧 output_tokens |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 432 | 4157 | 12792 | 256 | 678 |
| 2 | 725 | 6236 | 8788 | 384 | 830 |
| 3 | 438 | 4821 | 5368 | 7680 | 788 |

中位数 438 ms 对 4821 ms，本次样本降低 90.9%。独立搜索不调用聊天模型、没有该层模型 token 费用；旧层三次共 26,948 个 input_tokens、8,320 个缓存输入 token、2,296 个输出 token。用户任务最后组织答案的聊天模型费用仍然存在。只有 3 个同查询样本，可能受缓存和负载影响，不是所有查询的性能保证。
