## 1. 参考图直传：补齐客户端、云端与计费恢复链路

目标：用户选中的参考图，以真实图片数据交给图像模型。理解模型负责识别用途、补充约束，不能用一段文字概述代替图片输入。

实施方案：

1. 为每次任务建立不可变参考图清单：资源 ID、顺序、用途（风格/主体/布局/上一版成品）、MIME、字节数、SHA-256。主进程从已授权附件或用户明确选中的历史产物解析文件；模型不能任意读取其他本地路径。发送时固定字节版本，避免等待期间原文件变动。
2. 扩展 `stable_image_generate` 的结构化输入，用资源 ID 关联清单；由客户端读取并上传图片。无参考图继续走 generation；有参考图走受 Stable 登录保护的编辑路由。用户明确要求使用参考图时，缺图或不支持图片输入必须报明原因，不能静默退化成纯文字生成。
3. Stable Cloud 增加受限编辑代理，将校验后的图片上传到 OpenAI `/v1/images/edits`。同时更新客户端 `image-generation.cjs`、工具定义、云端传输和网关验证；仅删除提示词中的“不支持参考图”不算完成。GPT Image 2.5 已有官方图片编辑示例，可作为首批接入对象；GLM 图片输入能力尚未核实，不能直接宣称兼容。[官方示例](https://developers.openai.com/api/docs/guides/image-prompting)
4. 云端同步补齐图片输入费用预留、实际用量核算和账单结算，修改当前 `image_tokens !== 0` 拒绝逻辑。不能只放行上传而遗漏图片输入成本。接口返回区分文字/图片输入 token。[编辑接口](https://developers.openai.com/api/reference/resources/images/methods/edit)
5. 将参考图内容哈希、顺序、用途、编辑参数纳入客户端任务键及服务端请求指纹。超时后查询/下载同一任务；结果未知时禁止换路径重复付费生成。更新一张参考图应视为新任务，必须经过新的正常发送流程。

最强反例：图片编辑仍可能改动文字、Logo 或主体细节。对“原样保留、像素不变”的素材继续使用原图合成；对“允许重绘、只借鉴风格”的素材使用模型编辑。不能把直传参考图表述为严格保真保证。

验收：模拟供应商捕获实际 multipart 图片字节并比对哈希；验证多图顺序、上一版引用、失效资源、越权路径、透明图；更换参考图不能复用旧结果，同一请求恢复不能重复扣费。真实效果和费用需后续有预算的供应商验证，本轮不执行。

## 2. 业务规格：去掉默认补边，明确构图策略

目标：业务规格确定最终画布，默认不额外补白边或透明边；主体比例、裁切范围与输出尺寸都有明确约束。

关键限制：1138×292 海报约为 3.90:1；当前 GPT Image 2.5 文档规定输入尺寸长短边比例不超过 3:1，无法原生请求同等比例。现有标准档会请求 1536×512，再缩到 876×292 放入 1138×292 画布，左右各补 131 px。这是确定性的算法结果。[官方尺寸约束](https://developers.openai.com/api/docs/guides/image-generation)

实施方案：

1. 分离“最终交付尺寸”与“供应商请求尺寸”，按具体模型能力计算生成画布。最终尺寸不因模型对齐规则而改变；不要把 UI 的 32 px 对齐规则当成业务成品限制。
2. 移除业务提示词和成品函数中的无条件居中补边。比例一致时可等比缩放；轻微对齐差异也要按明确的安全区域处理，不能拉伸主体。
3. 比例差异明显时，让用户选择可理解的方案：推荐按目标版式重新构图，或在预览中确认裁切，或明确保留边距。对必须保留完整主体的超宽海报，先按目标位置规划主体/文字，再生成可覆盖画布的背景并合成；需要扩图时使用已支持的编辑流程。裁切只作用于用户确认的区域。
4. 纯色、纹理背景可在本地扩展时，应说明处理方式；无法可靠扩展时停在待处理状态。扩图属于额外生成，必须作为可见的新操作，不能为了达标自动重复扣费。
5. 为既有业务规格保留严格文件上限：头像 260×260/<5 MB，店招 750×422/<20 MB，海报 1138×292/<20 MB，弹窗 600×750/<2 MB，常规橱窗 702×532/<2 MB，菜品图 260×260/<2 MB。压缩失败不能悄悄降低交付尺寸或破坏透明度。

最强反例：比例不同的图片，不能同时做到“完整内容、比例不变、填满画布”而又不增补内容。简单把 contain 换成 cover 会裁掉主体，不能作为通用修复。

验收：六种规格均精确输出目标尺寸和文件上限；自动化样例验证比例保持、无算法补边、裁切区域授权和透明度；单独检查 1138×292 超宽海报。自然白色背景不应被误判为需要删除的留白。

## 3. 自定义尺寸：统一成品校验并覆盖最后一次修改

目标：界面展示并提交的交付尺寸，与最后交付的实际文件一致。模型声称完成、请求参数正确都不作为通过依据。

实施方案：

1. 建立统一成品规格：最终宽高、格式、背景/透明度要求、字节上限、数量、允许的适配策略；覆盖自定义和业务规格。自定义尺寸以用户最终确认的显示值为准，UI 自动对齐必须在发送前可见。
2. 将生成原文件与交付文件分开保存。原文件解码后读取实际尺寸；同一比例可执行明确的等比缩放，不同比例交给第 2 项策略处理。失败保留原图供排查，不能标成合格成品，也不自动重新生图。
3. 后续脚本合成/文字排版后的文件也必须通过主进程成品校验。交付收集时再次读取最后文件，核对宽、高、格式、字节数、透明通道要求、数量和内容哈希；仅靠模型调用一次检查工具不足以保证没有后续改写。
4. 交付记录保存预期规格、实测结果及文件哈希；发现文件被再次改写则校验失效，需要重验。旧历史图片不迁移、不重写；新任务通过带版本的交付记录使用新规则。

验收：供应商请求 1312×1024 却返回 1024×1024 时不能直接交付为成功；覆盖同比分辨率偏差、不同比分辨率偏差、损坏图片、超限文件、透明度丢失、多张少一张及生成后脚本改尺寸。业务规格和自定义走同一套最终断言。

## 4. 面板参数持久化：保存偏好，不覆盖请求快照

目标：修改面板后切换会话、重启应用仍能恢复最新值；已发送、排队或正在澄清的任务继续使用各自确认的参数。

实施方案：

1. 复用现有 `stable:agent:design` 校验及数据库设置能力，为每个会话维护带 revision 的面板偏好。`changeDesign` 立即更新 UI，并短延迟合并保存；关闭/切换时处理未完成保存，保存失败显示可重试状态。
2. 同一会话写入串行化，采用主进程版本校验，旧请求/旧响应不能覆盖新值。保存返回值只合并对应会话和对应版本，不能把用户切到另一会话的面板更新掉；多窗口冲突需刷新版本后保留用户最新编辑，禁止盲目覆盖。
3. 发送时复制当前参数为请求快照，并与本次消息绑定。删除 `runQueuedMessage` 用旧快照回写“当前偏好”的行为；后端直接验证请求自身携带的快照。为旧调用保留兼容读取规则，但不能将历史快照当成最近偏好。
4. 澄清答案续接原请求规格；后续用户修改面板只影响之后发送的新任务。数量冲突由明确的澄清选择改本次快照，不回写默认值。
5. 第 6 项的输入模式已单独保存在本地设置；后续若要并入数据库，使用独立 `inputMode` 字段。不要复用现有 Design 请求中 `generate/preserve` 的 `mode` 字段，它表达的是图像处理策略。

验收：不发送也能重启恢复；A/B 会话分别保存；快速连续修改与延迟写入不会回滚；队列中的 2 张请求开始执行时，面板新选的 4 张仍为 4 张；修改面板不改变历史参数、待执行快照或待回答的澄清任务。

## 推荐实施顺序

先完成第 4 项，使参数来源稳定；随后统一第 2、3 项的成品规格与校验；再贯通第 1 项客户端/云端的图片编辑、计费和恢复链路。第 2 项所需的模型扩图依赖第 1 项；依赖未完成时只能提供已实现且明确确认的本地处理方式，不能假装扩图可用。每阶段独立验证与交付，保留原文件和旧协议兼容，不批量改历史数据。

## 本次直接实现的第 5、6 项

5. Design 新会话以及旧 Design 会话下一次发送，理解、澄清判断和执行固定使用 `gpt-6.1-sol`，思考程度 `high`。执行层再次校验，防止会话参数或路由覆盖。所需模型/高思考能力不可用时明确报错，不悄悄回退其他模型。生图模型仍按原图片面板选择，普通会话和全局默认不变。
6. 发送、模型提问、回答澄清、任务完成后保持手动选择的“图片生成/对话”。切换会话、重新挂载应用后恢复对应会话选择；取消后恢复草稿也不再强制改模式。未曾保存选择的历史会话保留既有默认规则，用户选择后即记住。存储不可用时至少保持当前会话内的选择。
