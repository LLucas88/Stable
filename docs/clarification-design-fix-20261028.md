# Design 澄清卡片与数量冲突修复

## 原因

截图回复先输出说明，再输出 `[[STABLE_WAITING_FOR_INPUT]]` 与有效 JSON。旧解析器与流式过滤只支持标记位于开头，因此回复被当作完成正文，未创建等待问题卡片。用户确认本次确实未上传参考图，不属于附件丢失。

## 修复

- 识别说明文字后的独立协议标记，严格校验其后的问题 JSON，并保留前文为卡片说明。普通行内例子、代码块及无效结构不产生可操作卡片。
- 流式过滤支持任意分块位置的标记，保留此前说明，隐藏后续协议；最终内容仍经完整结构验证。
- 即使已产生部分产物，有效澄清问题仍暂停交付检查，不继续自动重跑。
- 按用户选择保持图片参数；明确数量指令与参数冲突时，先产生本地卡片，不调用额外判断模型。只有明确提交数量才继续，等待、关闭及“继续”不能自动选择。
- 数量识别保守限定为独立的中文生成指令（如“先生成1张”），排除图号、尺寸、引号内文案及含多种数量的表达。更复杂的数量语义仍交给执行前评估与执行模型，提示词要求先问再生成，不声称正则可理解所有表达。
- 确认另一数量只改变当前执行参数，原始消息和默认图片设置不改写；普通对话不添加图片参数。

## 验证

- 澄清、续聊、附件、Design 与新增边界回归 34 项通过。
- 实际 IPC 处理函数回归 22 项通过，含两种数量选择的执行参数验证。
- 隐藏 Electron 实际 AgentPage 回归 1 项通过，使用新解析器产出的卡片，验证显示、展开、选择、提交与后续对话。窗口与数据隔离，网络阻断。
- 类型检查通过。本地构建通过；沙箱内 Vite 模块解析失败，宿主环境重跑成功，保留已有 chunk 大小警告。
- 合计 57 项通过；没有付费模型调用，没有修改原账号或历史，不打包、不推送。旧历史中的原始 JSON 消息未追溯改写。
